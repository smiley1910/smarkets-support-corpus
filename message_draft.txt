Plain-English guide to using this page

This guide is for support agents who need to help customers with API errors without needing to understand the technical details behind the API.

Start with the customer’s exact words or error code. Use the Quick-Find Index or press Ctrl+F to search for terms like “401”, “token expired”, “order rejected”, or “rate limit”.

Read the “What it means” line first. This gives the plain-English explanation of the problem.

Use the “What to Tell the Customer” section. These sections are written as customer-facing guidance and can be copied or adapted into a reply.

Escalate when the guide tells you to. If the issue is unclear, persistent, server-side, or outside the listed patterns, flag it for technical support rather than guessing.

 How API Calls Work

A customer's application sends a request to https://api.smarkets.com. Smarkets responds with a three-digit status code that tells you whether the request succeeded or what went wrong.

Code range

What it means

Whose problem is it?

2xx (200, 201, 204)

The request succeeded

No problem

4xx (400, 401, 403, 404, 414, 429, 451)

The customer's request had a problem

Customer — guide them to fix it

5xx (500, 503, 504)

Smarkets' systems had a problem

Smarkets — log and escalate

Your role is to identify which problem the customer has encountered and provide the appropriate guidance. If the issue falls outside the patterns below, flag it for technical support.

 401 — Login / Token Issues ("Not logged in")

Common customer complaints — Ctrl+F these phrases: "I'm getting a 401" / "My token isn't working" / "It says AUTH_REQUIRED" / "I keep getting logged out" / "My session expired"

What it means: The customer's session token is missing, expired, or invalid.

 How it Works (Simple Explanation)

Using the Smarkets API requires a "session token" — like a ticket you get when you log in. Every request must present this ticket. The ticket is "valid for 30min, but if you make an authenticated request with it, it will be renewed for the next 30min." If the customer doesn't use the API for 30 minutes, the ticket expires and they need to log in again.

 Things to Check (in order)

Has the token expired? — Tokens last 30 minutes without activity. They need to log in again via POST /v3/sessions/ to get a fresh token.

Is the header formatted correctly? — The token must be sent in the Authorization header exactly like this:

Authorization: Session-Token <their_token>

Is two-factor authentication (MFA) enabled? — After logging in, MFA requires an extra step: POST /v3/sessions/verify/ with their TOTP code. Without this, the token is not fully authorised.

Did they switch from paper trading to live trading (or vice versa)? — Switching environments invalidates existing tokens. They need a fresh token from the new environment.

 What to Tell the Customer

Your session token has expired. Tokens are valid for 30 minutes without activity. To resolve this, log in again via POST /v3/sessions/ with your email and password to receive a fresh token. Once obtained, include it in the Authorization header using the format Authorization: Session-Token <your_token> for all subsequent requests. Note that login is rate-limited to 5 attempts every 5 minutes — if you receive a 429 during login, you must wait before trying again.

 When to Flag for Technical Support

401 on POST requests but GET requests work fine (possible mixed authentication methods)

The customer mentions "cookies", "auth v2", or "refresh tokens" (newer authentication schemes not covered here)

The error response contains data: None (no further detail to identify the problem)

The customer is getting 401 from the logout endpoint (DELETE /v3/sessions/) — this shouldn't happen normally

 400 — Bad Request / Wrong Data

Common customer complaints — Ctrl+F these phrases: "I'm getting a 400" / "It says REQUEST_VALIDATION_ERROR" / "The CSV export isn't working" / "INVALID_DATETIMES"

What it means: The data the customer sent is wrong — incorrect format, missing fields, or malformed parameters.

 How it Works

Validation errors always return a JSON body with "error_type": explaining exactly what's wrong. Read the data field — it tells you precisely what to fix.

 Common 400 Error Codes

Search for this code

What it means

Fix

INVALID_DATETIMES

CSV start/end times are wrong

Start and end "have to be separated by an hour, also these have to be exactly on the hour" (e.g. 2:00 PM to 3:00 PM)

BAD_REQUEST

Parameters are badly formed (markets/prices endpoints)

Check the parameter format

REQUEST_VALIDATION_ERROR

Something is wrong with the request

Read the data field — it tells you what to fix

RECKONATOR_REQUEST_TOO_LARGE

Account activity query is too broad

Narrow the date range or reduce filters

 What to Tell the Customer

The API rejected your request because something in the data was incorrect. The data field in the error response will tell you precisely what is wrong. Common causes: - Account activity CSV: the start and end times must be exactly on the hour (e.g. 2:00 PM to 3:00 PM) and exactly one hour apart - Placing an order: required fields such as price, quantity, contract_id, or side may be missing - IDs: event, market, and contract IDs must be in the correct format (numeric strings) - Too many IDs in one request: split the request into smaller batches (the API returns 414 REQUEST_TOO_LARGE when you exceed the limit) - Account activity request too large: narrow your date range. Check the error message carefully — it describes exactly what needs to be corrected.

 When to Flag for Technical Support

The data field in the error response is empty or unclear

You cannot determine which parameter is invalid from the error message

The customer asks for specific valid values for price or quantity (these require exchange tick knowledge)

Invalid price, invalid quantity, or other specialist order rejection codes (see Order Rejection section)

 414 — Request Too Large

Common customer complaints — Ctrl+F these phrases: "It says REQUEST_TOO_LARGE" / "I sent many IDs"

What it means: The customer sent too many IDs in a single request. The API has limits on how many IDs it will accept at once.

 Which Endpoints This Affects

Events, markets, contracts, and account activity endpoints that accept arrays of IDs.

 What to Tell the Customer

The API rejected your request because it contained too many IDs. You need to split your request into smaller batches. Try reducing the number of IDs you send at once and send multiple separate requests instead.

 When to Flag for Technical Support

The customer is unsure what the ID limit is per request

The customer needs to process a very large number of IDs efficiently

 429 — Too Many Requests

Common customer complaints — Ctrl+F these phrases: "I'm getting 429 errors" / "I've been rate limited" / "I keep hitting my rate limit" / "RATE_LIMIT_EXCEEDED"

What it means: The customer has exceeded their pre-approved rate limit. They need to wait before making more requests.

The error response includes three useful fields: limit (the approved maximum for that window), count (how many requests have already been made), and expiry (the ISO timestamp for when the limit resets).

 Known Per-Endpoint Rate Limits

Endpoint

Limit

Quotes (GET /v3/markets/{ids}/quotes/)

50 requests per 60 seconds

Login (POST /v3/sessions/)

5 requests per 300 seconds (5 minutes)

Cancel all orders (DELETE /v3/orders/)

1 request per 60 seconds

Cancel one order (DELETE /v3/orders/{id}/)

10 requests per second

Logout (DELETE /v3/sessions/)

30 requests per 60 seconds

Per Section 5 of the API terms: "exceeding them may lead to temporary suspension" and "repeated violations could result in API or account access being permanently revoked."

 What to Tell the Customer

You have exceeded your approved request budget for the current time window. Rate limits vary by endpoint and account, so do not assume there is one universal limit. Check the error response for limit, count, and expiry. Stop requests until the expiry time has passed. Common causes for new setups include polling quotes/prices too aggressively in a loop, or running multiple clients under the same account because they share the same limit. If your use case genuinely requires higher limits, contact api@smarkets.com to discuss; approval is not guaranteed.

 When to Flag for Technical Support

The customer is hitting limits despite very low apparent usage (possible multiple clients sharing the same account)

The customer's account has been suspended due to repeated rate limit violations

The customer needs assistance setting up WebSocket feeds

The customer mentions Cloudflare-based rate limiting rather than API rate limiting

 451 — Country Blocked

Common customer complaints — Ctrl+F these phrases: "It says COUNTRY_BLOCKED" / "I'm in the wrong country?"

What it means: Smarkets does not offer services in the customer's country or the country their IP address is coming from.

 What to Tell the Customer

Your location or account jurisdiction is not supported by Smarkets. This is a geographic restriction and is not related to your credentials or API setup. If you believe this is an error, contact support@smarkets.com to discuss.

 When to Flag for Technical Support

The customer is located in a normally supported country but is receiving this error (possible mismatched account jurisdiction)

The customer wishes to discuss jurisdiction restrictions

 Frequently Asked Questions

"How do I get API access?"

Submit the API Request Form. After approval, a £150 administration fee, or account currency equivalent, is deducted from their account balance. Per Section 3: "Should you choose to permanently withdraw from API usage within the first 60 days, your setup fee will be refunded." All new API accounts undergo a compliance review during this 60-day period (Section 2).

"Can I get the 0% commission?"

No. Per Section 3: "API customers are ineligible for any affiliate commission offers, as well as the 60 day 0% commission offer for new customers." Standard Customer Commission applies.

"Am I allowed to scrape odds or market data?"

No. Per Section 2: "All other uses are strictly prohibited, including but not limited to, odds scraping, concealing API calls, browser impersonation or reverse engineering." Violations may result in API removal, bet cancellation, account suspension or closure, and legal action.

"Can I share market data with a friend or third party?"

No. Per Section 5: "You may not share, sell or distribute platform data — such as prices, market status, events or business information — with third parties without written approval from Smarkets."

"How do I cancel an order?"

Use DELETE /v3/orders/{order_id}/ to cancel a specific order, or DELETE /v3/orders/ to cancel all open orders.

"How long does a session token last?"

Tokens are "valid for 30min, but if you make an authenticated request with it, it will be renewed for the next 30min." So as long as they use the API regularly, the token stays alive. Login is limited to 5 attempts every 5 minutes.

"What does a 504 error mean?"

A 504 Gateway Timeout means a Smarkets backend system didn't respond in time. Common codes: ZEUS_TIMEOUT (core trading engine timeout on order retrieval) and RECKONATOR_UNAVAILABLE (activity/reconciliation timeout). Retry after a short wait; escalate to api@smarkets.com if persistent.

"Which API endpoints don't need a token?"

Events, competitors, contracts, and currencies can be accessed without authentication. Market data endpoints (quotes, prices) require authentication. Prices without a token will be delayed. Session endpoints (login, logout, MFA) also don't need prior authentication.

API Terms & Policy Quick Reference

Use this section when a customer asks why API access has been refused, limited, suspended, or revoked. Keep replies factual and avoid making promises about approval, reinstatement, or market coverage.

Do not give the customer detailed internal reasoning for a suspension or compliance decision unless it has already been approved for customer communication. If the case is sensitive or disputed, escalate it.

Ongoing requirements after approval

API approval is not a one-off entitlement. Customers may be asked to provide details of their technical setup and how they intend to use the API. They must also keep Smarkets updated if their setup or intended use changes.

What to tell the customer: API access is subject to ongoing review. We may ask for information about how you use the API, including your technical setup and intended interaction with Smarkets. If that information is not provided, access may not be approved or may be removed.

Pre-approved events and markets only

API usage is restricted to pre-approved events and markets. If a customer cannot access a market or event through the API, it may be outside their approved scope.

What to tell the customer: API access does not automatically cover every event or market. Usage is limited to pre-approved events and markets. If you believe a market should be available to you, contact api@smarkets.com with the event or market details.

Benchmarking and competitive monitoring

Customers must not use the API or Smarkets data to benchmark markets, prices, liquidity, systems, or services for competitive purposes. This is separate from scraping and should be treated as a policy issue.

What to tell the customer: The API must not be used to benchmark Smarkets markets, prices, liquidity, systems, or services, including for competitive monitoring. If your intended use involves comparison or benchmarking, please contact api@smarkets.com before continuing.

Data extraction without trading

Customers must not use the API mainly to extract data without a reasonable level of trading activity. This can still be a breach even if the customer has valid API access.

What to tell the customer: API access is intended for approved trading-related use. Using it mainly to collect data without commensurate trading activity may lead to restrictions or removal of access.

Additional fees and restrictions

The £150 setup fee, or account currency equivalent, is not the only possible API-related cost or restriction. Some usage may be subject to specific restrictions and/or additional fees.

What to tell the customer: Some API use cases may require additional review, restrictions, or fees. If your use case is higher-volume, unusual, or data-heavy, contact api@smarkets.com for confirmation before proceeding.
