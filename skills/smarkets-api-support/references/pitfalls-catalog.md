# Pitfalls Catalog

Extracted from SKILL.md. Common mistakes and gotchas in Smarkets API support.


## Pitfalls
- **Speculating about undocumented API behaviour** — When a customer provides detailed evidence of a discrepancy the docs don't cover (e.g. quotes endpoint returns empty books in-play while the website shows prices), the correct instinct is to analyse the evidence and give your single best explanation clearly labelled as analysis, not fact. Avoid three specific traps: (1) Don't pile on multiple theories one after another when the first hypothesis is wrong — stop, incorporate the new evidence, and refine once. After two contradictory theories, escalate — don't reach for a third. (2) Be direct: give your conclusion upfront with one uncertainty marker, then stop. Don't layer caveats throughout the response — if the user has to say "be direct", you've already lost time. (3) Label every non-documented claim: "My best analysis says X because Y, but this is not confirmed by Smarkets docs." The validated approach is: analyse the evidence → give one weighted answer → then escalate the direct question to api@smarkets.com rather than cycling through increasingly speculative theories.
- Never promise IP whitelisting — it's not in the API docs
- API customers can't get promotional 0% commission or affiliate offers (Section 3 of T&Cs) — but they CAN get the volume-based Pro Tier (1%) by opting in. Don't conflate these.
- Commission tier confusion: customers asking about "API Pro Tier" or "being on 2%" usually need the three-tier explanation (Standard/Pro/Select), not a yes/no about their API status.
- The 60-day compliance review catches people off guard — 403 during this period is normal
- Don't confuse edge blocks (HTML 403 from CDN/firewall layer) with API auth errors — same status code (403), totally different fixes. JSON 403s with SOURCE_BLOCKED or IP_NOT_TRUSTED are IP-level blocks; HTML 403s are edge/firewall blocks.
- **451 COUNTRY_BLOCKED** exists — completely missing from many support teams' mental models
- **414 REQUEST_TOO_LARGE** means batch your IDs, not a validation error
- **504 ZEUS_TIMEOUT** means core trading engine timed out — distinct from 503 subsystem failures
- Account activity CSV datetimes MUST be on the hour, 1 hour apart
- Cancel-order rejections have their OWN set of codes (ORDER_CANCEL_REJECTED_*) — don't look for them under order placement codes
- Login itself can 403 with unexpected codes: USER_ON_TIMEOUT, SESSION_LIMIT_REACHED, DEVICE_NOT_TRUSTED, IP_NOT_TRUSTED, SOURCE_BLOCKED
- **Login field is `username` in the JSON, but the VALUE is the customer's email address** — Smarkets customers do NOT have a separate username. They authenticate with their email and password. The API schema field is called `username` (so `{"email": "..."}` will fail with REQUEST_VALIDATION_ERROR), but the value you put in that field IS the email: `{"username": "customer@email.com", "password": "..."}`. In customer-facing language, always say "email" — never "username", as customers don't have one. The previous audit (finding #1) incorrectly told agents to change "email" to "username" in prose — this was corrected June 2026.
- **Customer FAQ auth section has 5 known gaps (June 2026 audit)** — The `customer_faq.md` Authentication & Sessions section is factually correct but missing: (1) login returns **201** not 200 — spec confirms `"201: Token response for old and new auth v2"`; (2) MFA verify endpoint body not shown — schema `totp_login` requires `{"code": "123456", "token": "<limited_session_token>"}` where `token` is the limited session token from the initial login; (3) base URL `https://api.smarkets.com` not stated anywhere in the FAQ; (4) rate limit says "5 attempts" but spec says "5 requests" — successful logins also count toward the limit; (5) `Content-Type: application/json` not mentioned. These are low-severity for a FAQ but will generate support tickets from developers implementing against the spec. When auditing or updating the FAQ auth section, flag these as additions.
- **Default order type is `good_til_halted`**, not `good_til_cancelled`. The live spec shows `type` is OPTIONAL with `default=good_til_halted`. If a customer omits `type`, they get GTH behaviour (survives market going live, cancelled on halt/RF). This is a common source of confusion — customers who expect GTC are surprised their order survives the market going live.
- **Order type lifetime table (from live spec):** GTC = cancelled on market-live + halt + RF. GTH = kept on market-live, cancelled on halt + RF. KIP = kept on market-live + halt, cancelled on RF only. IOC = matches at placement time only. The spec has an explicit table — always reference it rather than paraphrasing.
- **`type` is optional, not required** — required fields for POST /v3/orders/ are: `market_id`, `contract_id`, `price`, `quantity`, `side`. `type`, `minimum_accepted_quantity`, and `label` are all optional.
- **⚠️ Market data endpoints work without auth (all three)** — `GET /v3/markets/{id}/quotes/`, `GET /v3/markets/{id}/last_executed_prices/`, and `GET /v3/markets/{id}/volumes/` are all marked `security: [{api_key: []}]` in the OpenAPI spec, but live testing (June + July 2026) confirmed ALL THREE return HTTP 200 with full data without any auth header. The quotes endpoint returns the full P2P order book (bids, offers, multi-level depth). The spec's own description confirms: *"If session token is not sent, these prices will be delayed."* Auth gets real-time prices; no auth gets delayed prices with lower rate limits. Do NOT tell customers these endpoints require auth to function. See `references/noauth-quotes-endpoint.md` for full evidence. **Note (July 2026):** The events endpoint parameter format changed — `type=football_match` (not `football`) and `state=live` (not `inplay`).
- **WebSocket/streaming is NOT in the API spec** — the documented API is REST-only via ``api.smarkets.com``. However, WebSocket streaming endpoints DO exist as Smarkets website infrastructure (``sio-live.smarkets.com``, ``sio-delayed.smarkets.com``, plus CFTC variants ``cftc-sio-live.smarkets.com``). These are hardcoded in the website's public frontend JavaScript and trivially discoverable by any visitor. They are NOT part of the public API and must not be referenced as API features. If a customer mentions ``sio-live.smarkets.com``, they found it by reading the website's JS bundles (DevTools). The correct response: the API is REST-only, streaming is not part of the documented specification. Take ownership and ask the customer to reply here with the use case rather than rerouting to ``api@smarkets.com``, since we ARE the API support team. Do NOT mention the CFTC product or CFTC endpoints to customers. See ``references/streaming-infrastructure-and-cftc-product.md`` for full endpoint inventory, the old deprecated SDK (``smk_python_sdk``, ``stream.smarkets.com:3801``, protobuf/TCP, now dead), and the CFTC "Smarkets Predictions" product intelligence.
- **``sio-live.smarkets.com`` is the website's Socket.IO endpoint, NOT from the deprecated GitHub SDK** — Customers may discover this hostname through browser DevTools and request IP allowlisting for it. It is not in any API documentation (old or new). The deprecated ``smk_python_sdk`` (``github.com/smarkets/smk_python_sdk``, copyright 2011) used ``stream.smarkets.com:3801`` with protobuf-over-TCP, a completely different protocol and hostname. Three tiers exist: old streaming API (``stream.smarkets.com:3801``, deprecated), current REST API (``api.smarkets.com``), and website Socket.IO (``sio-live.smarkets.com``, internal). See ``references/deprecated-streaming-api-and-sio-live.md``.
- **Paper trading is NOT in the spec** — the OpenAPI spec has zero mention of paper, sandbox, test, or staging environments. We reference paper→live token invalidation from internal experience, but cannot direct customers to a paper trading URL or explain how to access it. If asked, take ownership and ask them to reply here with what they need from a test environment.
- **"No monthly subscriptions or per-request charges" contradicts T&Cs Section 5** — the T&Cs say "API usage may be subject to specific restrictions and/or incur additional fees." Do not make absolute claims about no additional costs.
- **IP whitelisting is NOT in the spec** — say "IP whitelisting is not a documented feature" rather than "Smarkets does not offer IP whitelisting"
- **"You'll receive your API credentials" is misleading** — the API uses existing Smarkets account credentials (username/password). There are no separate "API keys" or "API credentials" in the spec. The T&Cs say "your API keys will be activated" but the actual auth is just the session token from the normal login flow.
- Login is rate-limited: 5 requests per 300 seconds
- The non-tech training module has been updated: includes full cancel-order table, login error table, 451/414/504 coverage, and the complete order rejection list from the live OpenAPI spec. Don't quote it to customers as a primary source — use it for triage, then cite the actual API docs.
- Training module is structured as a **Ctrl+F searchable reference** — Quick-Find Index at top maps 28 customer phrases to sections, every table has a "Search for this code" first column, and each section lists "What the customer may say" at the top with real queries agents can paste verbatim into the PDF. Maintain this pattern on updates.
- **Price denominator is 10,000, NOT 100,000** — Prices are basis points out of 10,000: `5000 = 50% = decimal odds 2.0`, `7194 → 7194/10000 = 71.94% → odds 1.39`. Formula: `decimal_odds = 10000 / price`. The "fraction contracts of 100000/1" terminology refers to the contract structure, not the API price denominator. Using 100,000 produces odds 10x too high (13.9 instead of 1.39). This error was made and corrected in June 2026 — see `references/noauth-quotes-endpoint.md` for conversion functions.
- **`coverage_delay` field is a static BetGenius config property, NOT a security vulnerability** — The `info.coverage_delay: 8` field on event states correlates with `is_betgenius_booked: true` and varies by event (null when BetGenius is not booked). It appears on PREMATCH events (set before kickoff), confirming it's a pre-configured property of the data feed, not a runtime measurement or public-access delay. Critically: the in-play bet acceptance delay that Smarkets uses neutralizes any front-running exploit — even if a trader knows the match state 8 seconds before Smarkets' data reflects it, they cannot get bets matched within that window because the acceptance queue holds the bet until the data catches up and the market suspends. The field should be filtered from public API responses as data hygiene (it's internal metadata with no consumer use case), but it is NOT exploitable and should NOT be reported as a security issue. **History:** This was initially mischaracterized as a "public-access delay" then corrected to "data-source delay" then finally downgraded to "informational" after the user confirmed the in-play acceptance delay. The lesson: (1) do not make confident claims about authenticated vs unauthenticated behavior without an authenticated comparison test; (2) always check whether a "leaked" field is actually exploitable before reporting it as a security issue — the existence of compensating controls (like bet acceptance delays) may neutralize the risk entirely.
- **Set-piece events do NOT void Instant Match bets** — only material events (goal, penalty, red card) void bets. Set-piece events (corner, dangerous free-kick) only extend the pending confirmation period. Bets are voided only if the set-piece leads directly to a goal (Rule 12.8.6.2). Do not conflate the two in customer responses. See `references/instant-match-voiding.md` for the full rule breakdown.
- **Rule 8.3.5 covers voids with no material event** — the scout feed can flag something that didn't actually happen, and Smarkets still voids (and won't reinstate). This is the rule that applies when a customer says "nothing happened but my bet was voided." Do not admit the feed was wrong to the customer — state the void confidently and cite 8.3.4 (protection against faster feeds).
- **Don't hedge in complaint responses** — if the rules support the action taken, state it confidently. Adding paragraphs like "the feed may have been wrong but we reserve the right not to reinstate" undermines the position and sounds both weak and cold. The verbatim rules quote does the work — let it.
- **Pro Tier is optional, not mandatory** — do not say customers "need to opt in to continue trading" when they exceed Pro Tier volume thresholds. Pro Tier (1%) is an optional opt-in. Customers can stay on Standard (2%) if they prefer — it may be more advantageous since Standard only charges on winnings, while Pro charges on both winnings and losses per matched bet. The commission-tiers reference confirms this.
- **Don't assume all EV displays are third-party overlays** — Old Smarkets had a native EV calculation displayed beside open positions. If a customer says "I see EV next to my position", acknowledge Old Smarkets as the source before considering third-party extensions. The absolutist claim "Smarkets doesn't calculate EV" is false for the legacy platform and will damage credibility with customers who have firsthand experience of it. Always distinguish: **open position EV** (legacy platform feature) vs **market page overlay** (third-party tool).
- **api.smarkets.com event type parameter format changed** (July 2026): The `type` parameter now requires the `_match` or `_outright` suffix (e.g., `type=football_match` not `type=football`). The `state` parameter changed from `inplay` to `live`. Old values return 400 `REQUEST_VALIDATION_ERROR`. Valid states: `new`, `upcoming`, `live`, `ended`, `settled`, `cancelled`, `suspended`. Customers referencing old parameter formats in support tickets may be confused — the migration was silent with no deprecation notice.
- **api.smarkets.com verbose error messages leak event type enum** (July 2026): Sending an invalid `type` parameter returns a 400 error listing ALL 47 valid event types (every sport, esports variant, special category like politics/tv_entertainment, and structural types). The `state` validation error similarly leaks the valid state enum. This is a complete market coverage map handed to anyone. Patch at `~/smarkets-audit/patches/09_error_sanitization.js`.
- **sbkscores.com leaks exchange metadata (WORSENING)** — The sbkscores.com API (owned by Smarkets) passes through exchange-internal fields without filtering. As of July 2026: 32 fields per match (was ~20 in June), 603KB per API response. Leaked fields include: `bet_allowed`, `bettable`, `inplay_enabled`, `parent_id`, `hasLiveStream`, `coverage_delay` (nested at `info.coverage_delay`, 206/319 matches), `actual_start_datetime`, `actual_end_datetime`, `competition.priority`, plus new fields since June: `clock`, `periods`, `periodScores`, `scores`, `quarters`, `round`, `stats`, `additional`, `hasLeagueTable`. sbkscores match IDs are identical to Smarkets event IDs (no remapping). Patches at `~/smarkets-audit/patches/04_api_field_filter.js`. See `references/sbkscores-security-audit-july-2026.md` for full audit.
- **sbkscores.com architecture is Next.js/OpenNext, NOT WebSocket or Rust** — The sbkscores.com API (`/api/v3/sports/*/matches`) is a Next.js API route handler running on OpenNext (serverless) behind Cloudflare. Headers: `x-opennext: 1`, `x-powered-by: Next.js`, `vary: rsc, next-router-state-tree, next-router-prefetch`. It proxies to `api.smarkets.com` — the `x-fetch-time` header reveals the proxy fetch latency. There is no WebSocket (WebSocket upgrade requests return normal HTTP 200). No Rust (no actix/axum/rocket headers). The API is cached at the edge (`s-maxage=10, stale-while-revalidate=50`) — live scores are up to 10 seconds stale.
- **Direct api.smarkets.com is faster than sbkscores.com proxy** — api.smarkets.com: ~140ms cached, ~340ms cache miss. sbkscores.com: ~175ms cached, ~832ms cache miss (includes 512ms proxy fetch time). For live pricing (quotes endpoint), api.smarkets.com is never cached (`cf-cache-status: BYPASS`) and consistently ~180ms. A trader or scraper would always hit api.smarkets.com directly.
- **sbkscores.com matches endpoint has NO rate limiting** — The `/api/v3/sports/*/matches` endpoint returns no rate limit headers and never returns 429, even under rapid burst (15 requests at 1.2s intervals + 5 rapid burst all returned 200). The health endpoint (`/api/health/`) DOES have rate limiting (`x-ratelimit-limit: 10`). The matches API is cached, which mitigates cost amplification — but varied query parameters could bypass cache and hit the backend directly.
- **Security audit red-team corrections (June 2026, re-verified July 2026)** — Several original audit claims were corrected during red-teaming: (1) DevSwrDebug is dead code (no-op stub with empty useEffect, returns null) — NOT a security issue, does NOT reveal API structure as originally claimed; (2) "No rate limiting" was partially overstated — health endpoint HAS rate limiting; (3) "coverage_delay is the most commercially damaging" was wrong — the in-play bet acceptance delay neutralizes it; (4) betsbk.com (PRODUCTION) also lacks all security headers — not just staging. **July 2026 update:** DevSwrDebug persists across rebuilds (chunk hash changed but code identical) — rebuilding alone doesn't remove dead code, the source must be modified. betsbk-staging.com now returns 503 (was 200) but is still publicly accessible — backend scaled down, not access-controlled. See `references/sbkscores-security-audit-july-2026.md` for the full re-audit.
- **Erroneous bet tickets: always check the 60-minute complaint window first** — The policy has two thresholds: ±15% (Section 4, voiding, requires complaint within 60 min) and ±20% (Section 3, outlier definition, allows investigation beyond 60 min). The complaint timing determines which applies. Do not flag the 15% threshold as "should have been checked" without first confirming the complaint was within 60 minutes — if it wasn't, only the 20% outlier threshold is available. See `references/clearly-erroneous-bets-policy.md`.
- **Erroneous bet calculation works in percentage price (probability) space, not decimal odds** — The policy's Section 1 states "price differences noted below are in absolute difference in percentage price." Example: 50% (2.0) is "10% different" to 40% (2.5) = 10 percentage points, NOT 10% of the decimal odds. A ±20% threshold means 20 percentage points in probability. Converting: fair odds 3.4 → 29.41%, minus 20pp → 9.41% → decimal odds 10.63. The "+1.00" in decimal odds (vs fractional) is the stake component — `decimal = fractional + 1.00`, equivalent to `1/probability`.
- **T&Cs Section 5 "benchmarking" prohibition vs Help Centre arbitrage promotion** — API T&Cs Section 5 prohibits "using the API to compare Smarkets' markets, prices, liquidity, systems, or services for competitive purposes." Meanwhile the Help Centre has articles teaching arbitrage with a calculator. Cross-exchange arbitrage isn't explicitly banned but overlaps with the benchmarking clause. Flag for `api@smarkets.com` rather than giving a definitive yes/no.
- **All ticket response drafts must be in ReST syntax from the first draft** — When asked to draft or correct a ticket response, output in ReST immediately, not plain text or markdown. Common ReST mistakes in ticket drafts: bare URLs (use `` `Link text <URL>`_ ``), no inline code for IDs (use double backticks), no block quotes for policy text (indent), Google text fragments in URLs (strip `` #:~:text= `` parameters), plain line breaks for sign-offs (use `` | `` line blocks). Reference: https://wiki.typo3.org/ReST_Syntax. Template: `templates/erroneous-bet-outlier-response.rst`.
- **Gemini Gem instructions must NOT use code block output — triple backticks break ReST parsers** — When engineering Gemini Gem instructions for ReST formatting (or any whitespace-sensitive output), three things are non-negotiable: (1) Do NOT tell the Gem to wrap output in a code block — triple backticks are not valid ReST and cause parse errors when pasted into the Smarkets ticketing system (verified with docutils: `` ``` `` triggers "Inline literal start-string without end-string" and "Possible incomplete section title"); (2) Keep instructions under ~7K chars — at 15K the Gem loses critical rules; (3) Include a complete worked example (real input → correct output) with a "STUDY THE EXAMPLE" callout — this teaches more than pages of rules. Show WRONG vs RIGHT patterns for persistent failures (Gemini defaults to Markdown and will produce hybrids like `` `text [url](url)`_ ``). The code block approach was tried as v5 and appeared to work (fixed indentation + Markdown contamination) but was proven wrong in v6 when the output was pasted into the actual ticketing system. Full engineering notes: `` references/gemini-gem-engineering.md ``.
