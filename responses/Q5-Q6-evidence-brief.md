## 1. API base + auth (Q5)

- Base URL: `https://api.smarkets.com` — OpenAPI `servers`: `[{"description": "Production", "url": "https://api.smarkets.com"}]`. All 18 public paths are `/v3/...`. Source: openapi/smarkets_openapi.json (servers block; also troubleshooting/common_api_issues.md "Key URLs").
- Auth = session token, NOT API keys/Bearer:
  - `POST /v3/sessions/` (login: `username` + `password`; schema `format: email`) returns a token. Header format per spec: `"Session-Token <your_token>"` in the Authentication/Authorization header. Security scheme in OpenAPI: `api_key`, type apiKey, in header, header name `Authorization`.
  - TTL: "The token is valid for 30min, but if you make an authenticated request with it, it will be renewed for the next 30min." Token response `stop` field: "This datetime specifies when the token will expire if not renewed. Any authenticated API call will automatically renew the token for another 30min" → 30-minute sliding window.
  - MFA (optional, per-account): `POST /v3/sessions/verify/` — flow: POST /v3/sessions/ for token, then POST this route with token + TOTP code. Errors include 400 INVALID_TOKEN, 403 LOGIN_VERIFICATION_REQUIRED / IP_NOT_TRUSTED / DEVICE_NOT_TRUSTED. Enable via smarkets.com/account/settings/login.
  - Auth v2 variant exists: `use_auth_v2: true` → token response includes `refresh_token` + `access_token` (spec `oneOf`); `remember: true` allows device token renewal after expiry.
  - Logout: `DELETE /v3/sessions/` (30/60s).
  - No separate API credentials in the auth scheme (internal knowledge base: API uses the customer's existing Smarkets login; the £150 administration fee activates access — T&Cs help page wording "your API keys will be activated" differs; see unverified).
- API-user gating: "In order to place bets and get the latest prices without restrictions using this API, you need to be a Smarkets API user." `POST /v3/orders/`: "This route only works for Smarkets API users, other users will receive a 403 status code response."

## 2. Rate limits (Q5)

Global default: **1200 requests per 60 seconds across all endpoints, per account** (spec `info.description`). On 429: error_type `RATE_LIMIT_EXCEEDED`, headers `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset`; most GET 429 bodies carry `{count, limit, expiry}` (quotes endpoint returns inline 429 — internal doc).

| Endpoint | Cap | Source (openapi path in smarkets_openapi.json, unless noted) |
|---|---|---|
| Any (global default) | 1200 req / 60 s, per account | `info.description` |
| GET /v3/markets/{market_ids}/quotes/ | 50 req / 60 s (API users; "rate limits for non-API users are lower") | `.paths./v3/markets/{market_ids}/quotes/.get.description` |
| POST /v3/orders/ | 10 req / s ("Rate limits are applied on an per account basis" also noted in docs/request_response_schemas.md) | `.paths./v3/orders/.post.description` |
| DELETE /v3/orders/{order_id}/ | 10 req / s | `.paths./v3/orders/{order_id}/.delete.description` |
| DELETE /v3/orders/ (cancel all) | 1 req / 60 s | `.paths./v3/orders/.delete.description` |
| POST /v3/sessions/ (login) | 5 req / 300 s | `.paths./v3/sessions/.post.description` |
| DELETE /v3/sessions/ (logout) | 30 req / 60 s | `.paths./v3/sessions/.delete.description` |
| POST /v3/sessions/verify/ | 429 documented; no numeric cap in spec | `.paths./v3/sessions/verify/.post.responses.429` |

- Overarching: T&Cs Section 5 "Smarkets will preapprove call limits per period. Exceeding them may lead to temporary suspension..." (scrape-aug18/help/api-tcs.md).
- Place-order rejection code `ORDER_REJECTED_THROTTLE_EXCEEDED` exists (400 responses of POST /v3/orders/); `ORDER_REJECTED_LIMIT_EXCEEDED` too.

## 3. Streaming (Q5)

- **Public API is REST-only.** The OpenAPI spec contains no streaming/websocket/socket paths. Market data = polling `quotes`, `last_executed_prices`, `volumes`.
- **Old streaming endpoint `stream.smarkets.com:3801` (protobuf/TCP+SSL)** was the deprecated `smk_python_sdk` (github.com/smarkets/smk_python_sdk; source `streaming_api/session.py` hardcodes host/port; repo ARCHIVED, last push 2019-01-08 — verified via GitHub API per skill reference). Endpoint reported NXDOMAIN (internal DNS check July 2026; skill notes the NXDOMAIN claim was not independently re-verified in every session — see unverified). Prior internal reply precedent: "the old streaming endpoint (stream.smarkets.com:3801, protobuf-over-TCP) was part of a deprecated Python SDK (smk_python_sdk on GitHub, copyright 2011, archived since January 2019) and no longer resolves."
- **`sio-live.smarkets.com` is the WEBSITE frontend WebSocket channel** (wss://sio-live.smarkets.com/ and sio-delayed; discovered inside public website JS chunk 7491), NOT part of the documented API and not available to API customers. Skill guidance: state it is not part of the documented API; the documented API is REST-only; do not promise streaming options.
- Internal note (HERMES_REFERENCE): API users must host servers in a licensed jurisdiction (UK, Sweden, Malta, Ireland; Finland not supported); Cloudflare blocks unsupported jurisdictions at the edge (403 HTML, not 451); datacenter IPs may be challenged and require internal allowlisting via api@smarkets.com.

You can stake larger amounts by placing multiple separate bets." (help-pages/.../212727285_Minimum_and_maximum_stakes.md).

## 5. Stake vs liability units, sizes, increments (Q6)

- Price = integer percentage basis points out of 10000: "This price is in percentage basis points. Example: 5000 = 50%. To convert it to decimal odds, just divide 10000 by it. Example: 10000 / 5000 = 2.0 (decimal odds). This price has to conform to a valid tick on the exchange; an invalid price error will be returned if it does not." Schema: integer, min 1, max 9999.
- Quantity = matched pot (back+lay), in 1/10000 currency units: "Quantity is the sum of the total pot (back+lay) in case the order is matched. The units are 1/10000 * one unit of the user's currency. Example: Quantity 500 = 0.05 GBP. To convert it to back stake, just multiply by the price and divide by 100000000. Example: 100000 (quantity) * 5000 (price) / 100000000 = 5 GBP back stake. The minimum stake is £0.05 or currency equivalent." (GET /v3/orders/ quantity wording: "The units are 1/100 of a UK penny" — same value, inconsistent wording in spec.) Schema min 0, max 4294967295 (uint32).
- Formulas (conversions): decimal odds = 10000 / price. Back stake (£) = quantity × price / 100,000,000. quantity(units)/10000 = pot (£, i.e. stake × odds on the back side).
- Lay liability: help centre formula "Liability = (Backer's stake * (Lay odds – 1)" (help pages 212105989_Bet_liability.md, 115003381865_How_to_calculate_the_liability_of_a_lay_bet.md; backer's-stake display is the default). Derived in API units: lay liability (£) = quantity × (10000 − price) / 100,000,000. DERIVED — not verbatim in API spec; see unverified. Liability/exposure is deducted from available balance ("available_balance ... is equal to the balance deducted by the exposure" — POST /v3/orders/ response; exposure also on GET /v3/accounts/).
- Minimum size in quantity terms: internal rag-context states min quantity 500 (=£0.05 pot). Not literal schema (min 0); spec only guarantees min stake £0.05. See unverified. Price increments: valid-tick table (help page 115003210649 "Why can't I bet at specific odds?"): 1.0001, then 1.01–2.00 in 0.01, 2.00–3.00 in 0.02, 3.00–4.00 in 0.05, 4.00–6.00 in 0.1, 6.00–10.00 in 0.2, 10–20 in 0.5, 20–30 in 1, 30–50 in 2, 50–100 in 5, 100–200 in 10, 200–300 in 10, then 300/500/1000/10000 (final cols). Two sides: "side buy: backing a contract; sell: laying a contract". Submit as integer basis points (e.g. decimal 2.0 = 5000).
- Matched at better price possible: "average_price_matched: This price can be different from the order price, as it may have been matched at a better price for the user, according to best price execution rules." Use `average_price_matched_precise` (basis points, up to 6 dp) "when deriving stake or returns from quantity to avoid rounding error, particularly after reduction factors are applied."

## 6. Partial fills, order types, idempotency/refs, timeout recovery (Q6)

- Partial fills supported: order states `created` (unmatched) / `partial` / `filled` / `settled`. POST response: `total_executed_quantity`, `executed_avg_price`, `orig_price` ("can be different from the matched price. This value will be null if there were no executions"), `available_quantity` (quantity left to match). GET /v3/orders/ adds `quantity_filled`, `quantity_unfilled` (+ `_user_currency` variants), `quantity_filled_pending` (8-second in-play pending confirmation; void of bets matched in preceding 8 s on material event — see multiples/void).
- Order types (POST): `good_til_halted` (DEFAULT), `good_til_cancelled`, `keep_in_play`, `immediate_or_cancel`. Lifecycle table (verbatim in spec): GTC cancels on market-live / halted / RF; GTH cancels on halted / RF (kept on live); KIP kept on live / halted, cancelled on RF. `minimum_accepted_quantity` (only for IOC): "If this minimum accepted quantity is not matched on bet placement time, the order will be cancelled and nothing will be matched." IOC returns when matched or cancelled; all other types "will return when the order is accepted by the exchange."
- Client refs/idempotency: **no client-generated order reference or idempotency key field exists** in the POST /v3/orders/ schema (fields: contract_id, label, market_id, minimum_accepted_quantity, price, quantity, side, type). Only user-supplied string is `label` ("Label is a user-defined string that will be stored in the order. It can be used to identify different trading strategies") — free text, no uniqueness/dedup guarantee. Server identity = `order_id` (returned on POST); `original_order_id` field exists on GET; `sequence_number` ties orders to the statement endpoint.
- Timeout recovery: 503 `CREATE_ORDER_TIMEOUT` / `ORDER_UNAVAILABLE` documented on POST /v3/orders/. Spec's own recovery pattern (non-IOC): "In the latter case, GET v3/orders should be used to check the status of the order, using the order id returned by this response." After a timeout the API may or may not have created the order → reconcile by GET /v3/orders/ (filters: `id`, `created_datetime_min/max`, `market_id`, `state`, `sequence_number_min/max`). No documented idempotent re-submission mechanism; dedupe is client-side via GET.
- Cancel: DELETE /v3/orders/{order_id}/ — 200 success; 404 `ORDER_CANCEL_REJECTED_NOT_FOUND`. Internal troubleshooting doc claims an already-cancelled DELETE "is idempotent - it succeeds regardless" — conflicts with the spec's 404; flag (unverified).
- GET /v3/orders/ returns "orders on Smarkets, these include open and recently settled orders." 504 ZEUS_TIMEOUT documented on GET.

## 7. Multiples: void/reprice/commission/settlement (Q6)

- Multiple/acca markets in API data: accumulator markets expose `contract_selections` ("the contract IDs that the acca is made up of") on GET /v3/accounts/activity/ and GET /v3/events/{event_ids}/markets/. `GET /v3/orders/fullcover/` returns "all fullcover orders for an account." Note: order placement for multiples is NOT in the public OpenAPI (website JS map shows undocumented /v3/multiples* endpoints — flag). Public API POST /v3/orders/ is single contract_id/market_id.
- Void/reprice rules (betting-rules/smarkets/general_rules_1-11.md, quote paths):
  - Rule 9.5 (accumulators, selections from different events): "9.5.1 If one selection is voided, the odds of the multiple bet will be reduced to account for the voided selection." "9.5.2 If a reduction factor is applied to any market in which a selection in the accumulator has been chosen from, the odds of the multiple bet will be reduced in line with this."
  - Rule 9.6 (bet builders, same event): "9.6.1 If one or more selections are voided or settled as a dead heat, the whole multiple will be voided with your stake returned. This will be the case regardless of the result of other selections. This includes a case where one or more selections have already lost." "9.6.2 In the case of horse racing bet builders, the full bet will be voided should a reduction factor be applied in any market included in the bet following the placement of said bet."
  - Help page "Multiples on Smarkets": same-event bet builder → one voided selection voids the whole bet; different-event multiple → odds reduced for voided selection; max 10 selections; "You cannot edit the price of a multiple"; no trade out; bet builders buy-only and not available in-play.
  - In-play pending void: quantity_filled_pending spec text (8-second pending; void of bets matched in preceding 8 seconds on confirmed material event — protection against courtsiding/faster feeds). Rule 8.2.1: "Bets submitted on an in-play market are subject to a four-second (horse racing & darts) or eight-second (all other events) betting delay before being placed into the market." Rule 8.3.5: "We will not reinstate already voided bets, so it is important to make sure your bet is confirmed."
  - General void authority: Rules 4.4–4.7 (delayed/voided settlement, resettlement, reversal of erroneous settlement), 5.1 (fraudulent/erroneous/technical-error voids), 8.1.x (post-off bets void).
- Commission: "As the original 2% commission exchange, our Standard Tier of commission is 2% on net profits per market only." (help 212654665 commission FAQ; also Pro 1% opt-in >1500 bets or >£1M staked/month; Select 3% >£25K net profit/12 months). API T&Cs §3: API customers ineligible for affiliate and 60-day 0% new-customer offers; standard Customer Commission applies. API fields: `commission` on account-activity items ("How much commission was charged"), `commission_type` on GET /v3/accounts/.
- Settlement reporting: GET /v3/accounts/activity/ "This information should be used for accounting reconciliation. This data is what is being used in our statement page"; hourly gzipped CSV via GET /v3/account_activity_csv/{start}/{end}/ (must be on the hour, exactly 1 hour apart); GET /v3/orders/ includes recently settled orders with `state: settled` and `outcome` (`winner`/`loser`/`deadheat`/`reduce`/`void`); contract `state_or_outcome` includes `winner`, `loser`, `deadheat`, `reduced` (RF applied), `voided`; `outcome_timestamp` = settlement datetime; `sequence_number` links orders to statement.
